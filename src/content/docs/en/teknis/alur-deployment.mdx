# Deployment Flow

> **Canonical source:** [PRD](/en/docs/proyek/prd) · [Sakala Architecture](/en/docs/proyek/architecture)

The Console sends user intent to the API. The API creates a command, and the Agent picks the work up outbound. No path lets a browser touch the runtime directly.

## Command lifecycle

1. The Console sends a deployment request to the API.
2. The API validates the request and stores it as a command.
3. The Agent polls for available commands.
4. The Agent claims a command before doing any work.
5. The Agent sends events and logs that have already been redacted.
6. The Agent reports success or failure to the API.

Polling only offers eligible work. The Agent may not execute a command until an atomic claim succeeds. A command that is already claimed or finished is not returned again as ordinary pending work.

## Deployment states

A deployment is an attempt, not an object that always succeeds. That is why each stage has its own name, so failure can be pinned precisely.

The health check runs before routing, because a route is only activated for an app that has answered. A deployment can skip a stage: `analyzing` is only reported for Railpack builds.

Because the stages are named, a failure message can say which stage stopped and what to check, rather than only `something went wrong`. The list of codes lives in [When a Deploy Fails](/en/docs/deploy-gagal).

Every deployment records the source commit, branch, trigger, actor, builder, runtime node, requested and applied resources, status, events, logs, image, route, health result, timestamps, and failure category.

Sakala does not guess arbitrarily. The order in which builders are chosen is fixed and explainable.

Repository analysis uses the Sakala scanner and `railpack info`. Real deployments use `railpack prepare` with BuildKit, rather than repeating the whole analysis chain.

The manual configuration in [ADR-008](/en/docs/proyek/adr) is not a builder of its own yet. What exists today are a project's build and start commands, which apply on top of those two builders. See [Preparing a Dockerfile](/en/docs/dockerfile) for the rules an application has to meet.

## Application routing

An application that runs successfully is mapped to a `*.run.sakala.dev` domain. In the local playground the same pattern is exercised through `*.run.sakala.localhost`.

Application containers join the runtime Docker network and publish no ports to the host. Caddy sits on the same network and forwards the public hostname to the container name and the port the API chose, for example `sakala-app-<project8>-<deployment-id>:3000`. That is why an application has to listen on `0.0.0.0:$PORT`, not on `localhost`.

Routes are written as files that are validated first, then reloaded.

## A deployment does not destroy a healthy one

A new deployment does not immediately tear down a running application. The Agent builds a candidate, starts it, then sends an HTTP request to `/` from inside the Caddy container. A status under 500 passes, and a 5xx is retried until the start deadline. Only then does the route move and the old container get removed.

If the candidate fails before the route moves, the previous version keeps serving, and the candidate's last lines of output are sent as logs before it is removed.

## Current status

As of 6 November 2026 the Agent and the API are connected through the Agent API: commands, events, logs, and results flow between them. This path was proven on staging on 1 October 2026. The HTTP health check, the stage order above, and the more detailed failure messages exist only on the `feat/core-maturity` branch. They have not been tested in production or used by pilot users. Sakala is not open to the public yet.

Operating modes and runtime limits are described in [How the Sakala Agent Works](/en/docs/teknis/agent).
