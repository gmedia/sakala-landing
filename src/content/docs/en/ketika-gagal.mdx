# When a Deployment Fails

Failed deployments are normal, especially the first one. What separates a good experience from a bad one is not how often it fails, but whether you can tell **where** it failed.

That is why every stage has its own name.

## Read from the bottom up

Logs are usually long. The error that actually matters is almost always **near the end**, not at the beginning.

The first red line you notice from the top is often a consequence, not the cause.

## Causes by stage

### Failing at `cloning`

The repository could not be fetched. Usually because it is private, the branch does not exist, or the repository name has a typo.

### Failing at `analyzing`

Sakala could not infer how to build your project. This happens when the structure is unusual or a manifest file is missing.

The fix is to provide a `Dockerfile` so you decide how it happens.

### Failing at `building`

The most common one. Usually one of:

- a dependency is used but not declared in the manifest;
- the language version differs from the one on your laptop;
- a build command fails because a required file was never committed;
- the build ran out of memory.

Test it by cloning into a fresh folder and building from scratch. If it fails there, the cause is not Sakala.

### Failing at `starting`

The image built but the application exited immediately. Usually a required variable is missing, a database connection failed, or the start command is wrong.

### Failing at `health_checking`

The application runs but does not answer on the expected port. This is the most confusing one because everything appears to have worked.

Three causes, nearly always:

1. The application binds to `localhost` instead of `0.0.0.0`. Inside a container, `localhost` means "only in here".
2. The application uses a fixed port instead of reading `PORT` from the environment.
3. The application takes longer to start than the health check allows.

The shape of explanation Sakala aims for looks like this:

```txt
Stage: Health Check

The application started,
but did not respond on the expected port.

Check:
- bind address
- exposed port
- runtime logs
```

### Failing at `routing`

The public address could not be activated. This is more often a platform-side problem than something in your code.

### Failing on `resource` or `timeout`

The application exceeded its memory or CPU allowance, or a stage ran too long. Heavy builds and memory leaks are the usual causes.

## A suggested order to check

1. Note which stage failed. That narrows things down fast.
2. Read the logs from the end.
3. Try the same step on a clean clone on your laptop.
4. Check that required variables are filled in.
5. If it stopped at the health check, check the bind address and port first.

## If you are still stuck

Sakala is not available as a public service yet, so there is no operational support. For now, documentation and website problems can be reported through the [repository issues](https://github.com/gmedia/sakala-landing/issues).

The failure categories on this page are also used internally to analyse the most common causes, so the error messages themselves keep improving.
