# Sakala Architecture

> Project-level architecture baseline — 2026-08-15

## 1. Architecture Goals

Sakala architecture should:

- keep product/business policy in the control plane;
- isolate privileged runtime operations in the Agent;
- allow Console and API to evolve independently;
- keep MVP deployment simple;
- leave a path to multi-node without building it prematurely;
- make deployment observable and recoverable;
- minimize privileged surface area.

## 4. Control Plane vs Data Plane

### Control Plane — `sakala-api`

Owns:

- identity;
- authentication;
- project;
- deployment metadata;
- desired state;
- environment/secrets metadata;
- resource policy;
- domains metadata;
- integration state;
- AgentNode/AgentCommand;
- events/log persistence;
- audit;
- future workspace/services/billing metadata.

Must not:

- access Docker socket;
- run user containers;
- perform `docker build`;
- mutate host Caddy directly from HTTP request;
- become remote shell.

### Data Plane — `sakala-agent`

Owns privileged execution:

- checkout;
- workspace;
- process execution;
- builder;
- image;
- container lifecycle;
- resource enforcement;
- logs;
- health;
- runtime routing;
- cleanup.

## 8. Agent Architecture

Mental model:

```text
protocol
→ language

core
→ brain/orchestration

runtime
→ hands/feet/host implementation

app
→ bootstrap/wiring
```

Dependency direction:

```text
sakala-agent-core
→ sakala-agent-protocol

sakala-agent-runtime
→ sakala-agent-core ports
→ sakala-agent-protocol

apps/sakala-agent
→ core + runtime
```

Core must not execute Docker/Caddy commands directly.

Runtime implements core-defined ports.

## 10. Builder Architecture

Priority:

```text
Dockerfile
→ Railpack
→ Manual override
```

Analyze:

```text
checkout
→ Sakala scanner
→ railpack info
→ stack preview
```

Deploy:

```text
checkout exact commit
→ Dockerfile build
OR
→ railpack prepare
→ BuildKit/buildx + railpack frontend
→ image
```

Do not run redundant `info → plan → prepare` for normal deploy.

## 11. Resource Ownership

```text
sakala-api
→ product resource policy

sakala-agent
→ enforcement

agent local config
→ node hard safety guard
```

Agent must not know product-plan semantics such as Free/Pro.

If requested resources exceed node hard maximum, explicit failure is preferred over silent major clamp.

## 14. Deployment Consistency

A Deployment is an attempt.

The currently healthy application should not be destroyed too early during a new deployment.

Desired future behavior:

```text
build candidate
→ start candidate
→ route/health candidate
→ switch active
→ retire previous
```

MVP may implement a simpler version, but architecture should avoid conflating:

```text
Project
= current container
```

## 16. Architecture Invariants

These should require an explicit ADR to change:

1. API never directly accesses Docker socket.
2. Agent is the privileged runtime boundary.
3. Product resource policy belongs to control plane.
4. Console does not own business policy.
5. API-agent wire contract is versioned.
6. Repository code is not merged back into a single Inertia dashboard by convenience.
7. MVP stays simple until validation justifies distributed complexity.
