# Alur Deployment

> **Sumber kanonik:** [PRD](/docs/proyek/prd) · [Sakala Architecture](/docs/proyek/architecture)

Console mengirim intent pengguna ke API. API membuat command, lalu agent mengambil pekerjaan secara outbound. Tidak ada jalur yang membiarkan browser menyentuh runtime secara langsung.

## Siklus command

1. Console mengirim permintaan deployment ke API.
2. API memvalidasi permintaan dan menyimpannya sebagai command.
3. Agent melakukan polling terhadap command yang tersedia.
4. Agent melakukan claim sebelum menjalankan pekerjaan.
5. Agent mengirim event dan log yang sudah melalui redaction.
6. Agent melaporkan hasil sukses atau gagal ke API.

Polling hanya menawarkan pekerjaan yang eligible. Agent belum boleh mengeksekusi command sebelum claim atomik berhasil. Command yang sudah diklaim atau selesai tidak dikembalikan lagi sebagai pekerjaan pending biasa.

## State deployment

Sebuah deployment adalah percobaan, bukan objek yang selalu berhasil. Karena itu setiap tahap punya nama sendiri sehingga kegagalan dapat ditunjuk secara spesifik.

Health check berjalan sebelum routing, karena route baru diaktifkan untuk aplikasi yang sudah menjawab. Sebuah deployment bisa melewati satu tahap: `analyzing` hanya dilaporkan untuk build Railpack.

Karena tahapnya bernama, pesan kegagalan dapat menyebut tahap mana yang berhenti dan apa yang perlu diperiksa, bukan sekadar `something went wrong`. Daftar kodenya ada di [Saat Deploy Gagal](/docs/deploy-gagal).

Setiap deployment mencatat commit sumber, branch, pemicu, aktor, builder, runtime node, resource yang diminta dan diterapkan, status, event, log, image, route, hasil health check, waktu, serta kategori kegagalan.

Analisis repository memakai scanner Sakala dan `railpack info`. Deployment sesungguhnya memakai `railpack prepare` bersama BuildKit, bukan mengulang seluruh rangkaian analisis.

Konfigurasi manual di [ADR-008](/docs/proyek/adr) belum menjadi builder tersendiri. Yang sudah ada adalah build command dan start command project, yang berlaku di atas kedua builder tadi. Lihat [Menyiapkan Dockerfile](/docs/dockerfile) untuk aturan yang perlu dipenuhi aplikasi.

## Routing aplikasi

Aplikasi yang berhasil dijalankan dipetakan ke domain `*.run.sakala.dev`. Pada playground lokal, pola yang sama diuji melalui `*.run.sakala.localhost`.

Container aplikasi bergabung ke Docker network runtime tanpa mempublikasikan port ke host. Caddy berada di network yang sama, lalu meneruskan hostname publik ke nama container dan port yang dipilih API, misalnya `sakala-app-<project8>-<deployment-id>:3000`. Karena itu aplikasi wajib mendengarkan di `0.0.0.0:$PORT`, bukan di `localhost`.

Route ditulis sebagai berkas yang divalidasi lebih dulu, baru kemudian dimuat ulang.

## Deployment tidak merusak yang sedang sehat

Deployment baru tidak langsung menghancurkan aplikasi yang sedang berjalan. Agent membangun kandidat, menjalankannya, lalu mengirim permintaan HTTP ke `/` dari dalam container Caddy. Status di bawah 500 berarti lolos, sedangkan 5xx terus dicoba sampai batas waktu start. Setelah itu baru route berpindah dan container lama dihapus.

Kalau kandidat gagal sebelum route berpindah, versi sebelumnya tetap melayani, dan baris terakhir output kandidat dikirim sebagai log sebelum ia dihapus.
