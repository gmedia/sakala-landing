# Sakala Landing Philosophy

> **The landing should behave like Sakala: turn an abstract idea into something the visitor can feel and understand.**

## 1. The fundamental question

Do not begin with:

```text
What features does Sakala have?
```

Begin with:

```text
Why does Sakala need to exist?
```

The answer is not Docker, Railpack, Caddy, an Agent, or a dashboard.

Those are mechanisms.

The deeper problem is:

> A software project can be complete as source code while still not be present in the world.

A repository can preserve code.

A local development server can prove that code runs.

Neither automatically gives the work a life outside its creator's machine.

Sakala exists in that gap.

## 2. Core philosophical model

```text
POSSIBILITY
Something could exist.

      ↓

PRESENCE
Something now exists in a form others can reach.

      ↓

CONTINUATION
Its existence makes new work possible.
```

This model should govern the homepage.

### Possibility

Source code is structured potential.

It contains an idea, intent, and capability, but a visitor cannot necessarily experience the result.

### Presence

A work becomes meaningfully present when it can:

- run;
- be reached;
- be opened;
- be used;
- fail in reality;
- be repaired;
- be shared.

Deployment is the technical process that helps create this presence.

### Continuation

A living work can continue beyond its original purpose.

```text
Project
→ Live Application
→ Showcase
→ Learning
→ Template
→ Inspiration
→ New Project
```

This is why Explore, templates, creator attribution, collections, and learning are philosophically related to deployment rather than random future features.

## 3. The Life of a Project

The central creative concept is:

# **The Life of a Project**

The homepage follows one conceptual project through its life.

```text
Idea
↓
Source
↓
Repository
↓
Local
↓
Sakala
↓
Analyze / Build / Run / Reach
↓
Live Application
↓
Share / Learn / Improve
↓
New work
```

The project is the protagonist.

Sakala is not the protagonist.

Sakala is the system that helps the protagonist cross from possibility into presence.

This distinction matters.

The landing must celebrate what people create, not infrastructure sophistication.

## 4. The Threshold

`The Threshold` is a signature visual metaphor, not the whole story.

It represents the transition:

```text
SOURCE / LOCAL / POSSIBILITY
              ↓
            SAKALA
              ↓
APPLICATION / PUBLIC / PRESENCE
```

The Sakala mark may participate in this transformation if the implementation respects the real logo geometry.

Do not invent a mystical portal aesthetic.

The threshold should remain precise, technical, and recognizably Sakala.

## 5. Emotional refrain

The human meaning of Sakala can be reduced to:

```text
"I built this."
      ↓
"Here it is."
```

The distance between these two statements is the emotional territory of Sakala.

The first proves authorship.

The second proves presence.

Use this refrain sparingly. It should feel discovered, not repeated as a marketing slogan.

## 6. The meaning of green

Green Teal is not merely "the primary button color."

For the landing, green gains narrative meaning:

```text
manifestation
life
presence
growth
health
continuation
```

The page should not be saturated with green from the first pixel.

A stronger pattern is:

```text
Possibility
→ mostly neutral

Transformation
→ Green Teal enters

Presence
→ Green Teal becomes confident

Continuation
→ Green Line branches and grows
```

The color appears because something is becoming alive.

Do not translate this into eco imagery.

No leaves, planet icons, generic sustainability gradients, or unsupported environmental claims.

## 7. Seven Sakala principles as experience

The homepage should not need seven feature-style cards explaining the principles.

The principles should be experienced:

| Principle | Landing expression                                         |
| --------- | ---------------------------------------------------------- |
| Wujud     | source becomes reachable application                       |
| Purna     | journey continues through health and public reach          |
| Sederhana | visitor is not forced through infrastructure ceremony      |
| Terang    | failures and automatic decisions can be explained          |
| Tumbuh    | project can evolve beyond first deployment                 |
| Berbagi   | live work can become showcase/template/inspiration         |
| Manusia   | artifacts and infrastructure remain in service of creators |

A separate Philosophy page may explain them explicitly.

The homepage demonstrates them.

## 8. Depth without confusion

Sakala should be philosophical without becoming obscure.

The intended pattern is:

```text
simple words
+
large idea
+
concrete proof
```

Good:

> Kode dapat selesai ditulis.  
> Tetapi belum tentu selesai diwujudkan.

Bad:

> Sakala mengaktualisasikan ontologi artefak digital melalui proses manifestasi komputasional.

The landing is not a philosophy lecture.

It is a moment of recognition.

## 9. Product honesty

A philosophical website becomes dishonest if its product proof is fake.

Therefore:

- do not imply unfinished capabilities are production-ready;
- do not invent customers or testimonials;
- do not show fake screenshots as if they are live product;
- do not present future Explore/Learn states as shipped without labels;
- do not claim scale, uptime, enterprise readiness, zero-ops, or sustainability without evidence.

Sakala's philosophy includes `Terang`.

The landing must practice it.

## 10. Final test

For every section ask:

> Is this section explaining Sakala, or helping the visitor experience Sakala?

Explanation is sometimes necessary.

Experience should dominate.

And for every visual or feature claim ask:

> Does this help a human understand how a work becomes real, or are we only showing infrastructure because we enjoy infrastructure?

If the second answer dominates, remove it.
